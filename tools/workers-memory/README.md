# Workers memory measurements

From the repository root, against the built TypeScript package:

```sh
node tools/workers-memory/run.mjs
```

This regenerates every measurement table and the evidence for the limit-setting
table in [the Workers guide](../../docs/workers.md), including the preparation
acceptance table. It prints Markdown tables and writes those tables plus all raw
observations and the Wasm build identity to `target/workers-memory/`. It needs no
network, sockets, additional npm dependencies or workerd. Use a supported Node
version; the recorded guide uses v22.23.0. Allow several minutes without parallel
builds or benchmarks. Timings are single cold observations, not performance gates.

If the package is not built, first follow its [build instructions](../../packages/typescript/README.md#first-useful-result).
An optional positional argument selects another built package directory:
`node tools/workers-memory/run.mjs /path/to/package`.

The instrument is the SDK Wasm instance's `memory.buffer.byteLength`, reached
through the built bindings for measurement only. Every row and every binary
search trial runs in a fresh Node process. Before/after preparation excludes
document validation and resource registration; growth is their difference.
Freed capacity is reusable, so zero growth does not mean zero allocation.
This is neither live allocation nor process RSS. No platform quota is simulated.

The deterministic generators preserve the guide's 2026-11-14 lab shapes:
many-description operations, nested object schemas, dense arrays/objects, copied
identifiers, eight-property records, pointer chains and the hostile pattern.
Only workloads cited by the guide are included. This tool is separate from
`runtime-qualification`: that tool has a frozen multi-host/archive protocol and
requires browser/workerd sockets; this one observes a built package in Node.

For contained records at 10/100/300/1,000/3,000 and chains at
1,000/4,000/16,000/49,000 links, binary search keeps a refused lower endpoint and
a completing upper endpoint until their gap is at most 1% of the lower endpoint.
Both endpoints and growth at the completing allowance are recorded. The search
uses nondefault reservations below 512 MiB, selecting Original with all other
limits default. Ratios divide the completing allowance by growth; zero growth
has no finite ratio. The 8/16/32/64 MiB capacity table tests every listed size
directly and reports the largest **tested** completion, not an absolute maximum.

The runner asserts conformance for the ordinary document tables, satisfaction
for default preparation rows and completing search endpoints, typed preparation
refusals, and successful follow-up small preparation/evaluation after every
preparation. Unexpected errors fail the command. The guide's dated workerd-only
RSS, first-use and isolate-stall observations are not regenerated by Node.

## Entry disposal

The runner also includes `disposal.mjs`, a Node adaptation of the Workers lab's
m7 `dispose-step` experiment: `docMany(20000)` has 27 operations, setup counts
those operations, then one synchronous turn calls `operations()` 10,000 times
without disposing the results, yielding or explicitly invoking GC. There is no
separate 10,000-request prelude. Run just this probe with:

```sh
node tools/workers-memory/disposal.mjs
```

Measured on 2026-11-15 with Node v22.23.0, Darwin arm64, the saved owner-rulings
baseline at `1159bc32` and this detached-record implementation:

| Package | Calls | Before bytes | After bytes | Growth bytes | Growth MiB |
| --- | ---: | ---: | ---: | ---: | ---: |
| Entry-owner baseline | 10,000 | 2,883,584 | 13,172,736 | 10,289,152 | 9.8125 |
| Detached entry records | 10,000 | 2,883,584 | 2,883,584 | 0 | 0 |

These are Wasm linear-memory capacities, not live allocation, JS heap, RSS or a
Cloudflare quota. Released capacity does not shrink. The runner asserts the
current zero-growth result. Entry records have no Wasm owners; this does not
remove the pinning cost of `Schema` or `ExactJson`, which can retain their whole
document until disposed or finalized after the proof itself is disposed.

## Entry read timings

Save a built baseline's `dist/` and `package.json` before changing the facade,
then build the candidate and run, with no other builds or benchmarks in parallel:

```sh
node tools/workers-memory/entry-reads-run.mjs target/entry-baseline packages/typescript
```

The runner alternates baseline/candidate order in separate fresh processes for
10, 1,000 and 10,000 operations, runs the scalar-only variant, and repeats the
disposal probe. It writes all 11 samples per cell, medians, build identities and
Markdown tables to `target/entry-timings/`. `entry-reads.mjs` can run one package
and size independently, using `node --expose-gc`.

The fixture declares a description, one alias, two tags, false deprecation and a
string input schema. Parsing, validation and proof retention/disposal are outside
the timing interval. Required entry and schema disposal is included. The fresh
wrapper cells use a fresh proof wrapper per call over warm Rust snapshot indexes.
Neither implementation caches records. `operations` reads every key; `operation`
reads no field; `operationField` reads a key; `inputSchema` acquires and disposes
a schema. The scalar variant omits aliases and tags without changing the method.

The runner writes its raw samples and build identities to `target/workers-memory/`.
Measured on 2026-11-15 against the previous owner API: listing and reading keys
improved 61-65%, lookup plus a key 75-79%, and schema acquisition 30-43%. A lookup
that reads no field became 60-190 ns slower (0.708-0.806 microseconds warm, 0.770-0.879
with a fresh wrapper), a cost accepted when the records were adopted. A
field-reading benchmark is not a substitute for the lookup-only row.

## Registration and the complete guide recipe

Supplied resources in every preparation row now receive that row's
`preparationLimits` during registration. A registration refusal is recorded as
`register`, separately from a preparation refusal. The complete-recipe table
uses the option objects in `guide.mjs`, checked against the guide's code block
by the built-package `registration-storage.test.mjs` test. It runs every listed
shape through bounded document parsing, validation with 100 findings, bounded
resource parsing, registration, preparation, bounded value parsing and exact
value evaluation. Both the constructor and `with()` are exercised. A refusal
stops that row and identifies its stage. Contained workloads register a Boolean resource; document-only annotation
shapes also select that Boolean schema for the later stages. Other contained
workloads select their documented schema, and every original document remains
alive. All owners stay alive until that synchronous recipe finishes.

The starting recipe reserves 16 MiB for registration and preparation, and 4 MiB
for evaluation. The large-chain variant uses 64 MiB for preparation and 8 MiB
for evaluation. The table also records the 49,000-link chain's evaluation refusal
at 4 MiB, even when its preparation has 64 MiB.

Registration's charge is qualified natively: the public API regression
`crates/openbindings/tests/registration_accounting.rs` covers shared owners, URI-heavy schemas, chains and detached subtrees against
`tools/allocation-test-counter`, requiring a factor from 1.0 through 1.7.
