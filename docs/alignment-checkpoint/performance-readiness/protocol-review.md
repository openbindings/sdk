# Matched original-default performance protocol review

This is an independent protocol/source audit, not a performance PASS. No timed measurements were used to choose expected results. Baseline authority is the pristine `18a66957d038431a5caf0db340d96f60bc1decdf` archive at `work/performance-baseline-18a66957-rust199`; candidate is the `df06588bb8c07251b2f15e5121f2456634c99dfe` archive. The earlier statement about three removed workloads came from another pre-existing working copy and is withdrawn. No build or measurement used that incorrect comparison.

## Permitted paired construction

The explicit coordinator-owned matched driver is a reasonable bounded protocol. It must not be represented as accepted by the generic compare.py automatic cross-API builder: that builder correctly rejects the raw driver/third-party lock differences. Keep the generic checks unchanged.

Both `tools/evaluator-matched` trees have byte-identical current `main.rs`, `allocations.rs`, `build.rs` and `Cargo.toml`. Their SDK adapters remain version-specific. The one common driver change adds the preparation-refused outcome counter outside the measured region. It still changes the BTreeMap layout used by the timed loop, so measuring the original old binary against the new binary would be invalid; both sides must be rebuilt with this same driver.

The independent archive check compared268 baseline and429 candidate files under crates/vendor and root Cargo.toml/Cargo.lock to their exact Git blob identities: no mismatch. The matched adapters and lockfiles initially match each side's own archived benchmark adapter/lock byte-for-byte. Root Cargo manifests are recorded separately because the existing embedded SDK digest covers crates/vendor rather than every Cargo workspace input. Matched driver edits must never modify the SDK archives' crates or source selection.

Use four fresh target directories for baseline/candidate × timing/allocation, identical Rust1.99 toolchain target/profile/link flags, and the respective locked dependency closure. Retain commands, environment flags, binary hashes and reported SDK/instrument digests; recompute those digests from the actual trees and reject mismatches before measurement. Capture actual Cargo feature/dependency trees for each side. Shared registries are acceptable; reused target outputs are not evidence of a fresh correct pair.

## Workloads and outcomes

The exact18a fixture source matches the archive. Both baseline and candidate have42 workloads; every request object after removing only `expected` is identical, including source strings, options, resources, mode lists and input bytes. There are no removed, baseline-only or candidate-only workloads in this pair.

The eight current evaluator expectation changes are independently justified in `outcome-dispositions.json`. The intermediate current expectation `preparation-refused` for missing local pointer is not the baseline oracle: the18a adapter represents its old preparation refusal as `no-verdict/non-schema-target`. Preserve that historical observation. The candidate must return a reached Undefined result with semantic-dependence and the original reference location, rather than converting an ordinary undefined predicate into a preparation failure.

Seven document/read expectations also differ from18a because they now include the current complete report and c1419c9/OBI-14 evidence. Under the existing comparison policy, the final15 changed-expectation workloads produce19 checked observation-only mode rows. The remaining27 workloads yield82 comparable mode rows, out of101 total. Do not advertise all42 as same-output timing/heap comparisons. Do not normalize away diagnostic fields or report provenance to make changed rows look equal.

A future separately reviewed metadata-drift lane could compare equivalent caller work after checking both full outputs, but it is unnecessary for the initial strict run. Status/policy-changing missing-pointer and historical-depth rows must remain distinct. A faster refusal is never completion of the required positive job. The historical evaluation_depth field is consumed only by the benchmark adapter to replay that old request; it is not restored as a current SDK option, nor an equivalent resource-policy comparison.

## Adapter and phase audit

Both versions parse the same root schema and supplied resources, validate the same minimal interface document, retain its proof/resources/evaluator in Context, and resolve operation `op` on every preparation. The baseline's required trait-object owners and candidate's typed owners are authentic public-API costs. No benchmark shim precomputes a verdict or substitutes a validation implementation.

`eval` and `explain` retain preparation and parsed value before timing. `context` retains proof/resources/evaluator but prepares/drops a fresh owner each iteration. `compile` includes context construction, document proof, resource parsing, preparation and owner destruction. `full` includes those operations plus input parsing and evaluation. `cold` times a single first-use preparation and retains its owner until after timing. `document` includes report and proof acquisition/destruction; `read` retains the proof and traverses the same keys, aliases, descriptions, tags and schema presence, checked against exact independent counts. Serialization remains outside timing. Current and baseline details are selected before entering timed loops.

**R-PERF1, readiness guard:** both initial adapters' `Prepared::is_ready` return true for any non-cancelled error. Timed compile/context can therefore count an unexpected preparation refusal as `prepared`, despite a successful initial precheck. Strengthen readiness to actual `Result::is_ok` in both matched adapters (and the current benchmark adapter), or give intentionally measured refusal completion a separately named, separately checked operation. None of the82 comparable modes needs a failed preparation counted as readiness. Preserve the initial source hashes; add a negative preparation-limit probe and refresh all four binaries/provenance after correction. Until this is done, the protocol has this open harness finding.

## Dependencies and measurement policy

The lock audit finds24 added registry identities, all exact existing candidate-root pins; none removed or upgraded. The common graph changes are jsonschema's required IDNA feature closure and the evaluator's direct regex-automata/regex-syntax dependencies replacing its direct regex edge. These are real SDK implementation requirements, not arbitrary benchmark upgrades. Do not force candidate features on the baseline merely to make lockfiles look equal. Optional jsonschema peer observations must disclose Cargo feature unification; they are not a common semantic oracle or a portable engine-only comparison across differing closures.

Retain strict full-observation assertions, exact request replay, all modes, randomized adjacent paired children, required sample counts, allocator instruments and workload-carrying baselines. Keep requested-heap/allocation-count gates active, timing/RSS advisory as already documented, and no new accepted residuals without their separate evidence/decision. Run timing when the competing qualification builds have finished; preserve noise/inconclusive results rather than selecting a favorable rerun. Scope completion claims to the82 comparable mode rows plus the19 independently checked changed rows, with every observed failure or resource flag retained.
