## 2. Scope and completion claim

Migrate the maintained Rust SDK, its default evaluator, evaluator qualification kit, HTTP
companion, interface companions, private Wasm bridge, and existing public TypeScript surface.
Replace the retired inspection/synthesis companions with the current source-puller and
kind-descriptor capabilities. Migrate SDK-owned examples, consumers, docs, tests, package
metadata, and qualification tooling with them.

TypeScript's existing document, evaluation, and discovery capabilities must match Rust's
semantics. Public TypeScript adapters for the optional role interfaces do not exist today;
adding them is a distinct host-API work item, not an implicit result of compiling the Rust
roles to Wasm. Record their absence in the capability matrix. Rust role portability still
needs its promised Wasm checks. No documentation may imply role parity that has not shipped.

The standalone OpenAPI kind implementation is a downstream integration, not a dependency of
core or of the SDK workspace. Its migration is tracked separately and requires its own exact
revision, kind definition, and evidence before any cross-project claim. Legacy Go/independent
TypeScript repositories, CLI/application migration, publication, and deployment are outside
this SDK plan. Other optional interfaces (document-store, delegate-manager, software-descriptor,
token-provider) remain readable OBI contracts; they do not require new runtime products here.

Document-model alignment and evaluator capability are separate claims. Stage 0 freezes an
explicit capability matrix: required document answers, supported value-evaluation cases,
declared evaluator limits, role APIs, and hosts. A truthful no-verdict can be sound without
meeting an expected value-evaluation capability. Record that as a gap, never a corpus pass or
an excuse to redefine the specification. Reassess inherited limits rather than treating them
as protected behavior.

## 3. Alignment is a design constraint

Derive the target model from the publications first, then compare the code to it. Do not start
by assigning every existing class a new name. Do not assume that the old inventory's 1,522
"SDK-necessary" classifications entitle those concepts to survive.

Every public concept, substantive internal subsystem, taught term, and policy gets one entry
in an alignment map with:

| Entry field | Required content |
| --- | --- |
| Concept and meaning | One definition and its relationships, independent of implementation |
| Authority | Pinned section/rule/interface, or an explicit implementation justification |
| Classification | Spec concept; interface/profile concept; implementation mechanism; SDK policy; or obsolete |
| Representation and owner | Rust/TypeScript API, owning module/crate, and retained data/proof |
| Behavior | Invariants, transitions, effects, failure outcomes, and limits |
| Evidence | Positive/negative witnesses and the checks that establish the claim |
| Disposition | Keep, reshape, merge, move, replace, or remove; reason and completion status |

For an implementation mechanism, name the concrete need: Rust ownership/lifetimes, exact JSON,
revision-safe views, asynchronous I/O, bounded work, source diagnostics, compilation, host
interop, or another demonstrated requirement. Also state why a simpler representation fails,
why the mechanism is public if it is public, and which domain relationship it implements.
"The code uses it" and "the spec does not forbid it" are not sufficient reasons.

SDK policies are a separate category. Examples include requiring conformance before a checked
invocation, rejecting a malformed provider result, or imposing a size limit. They are useful
choices, not necessary consequences of Rust or new specification requirements. Give them an
owner, an explicit outcome, and tests; do not present them as portable contract semantics.

Acceptance has five dimensions:

1. **Terminology:** the same concept uses the same term across code, docs, diagnostics and
   examples. A language-specific casing convention is fine. A synonym with no distinct meaning
   is not. Legitimate uses of "source", "resource", "content" or "contract" are judged in context.
2. **Meaning:** invariants, references, presence, claims, and failure distinctions match their
   authority. A convenient representation must not change what an OBI says.
3. **Organization:** the code's ownership and dependency graph follows the domain's boundaries.
   Related concepts have discoverable homes; unrelated role behavior does not collect in core.
4. **Representation:** builder, view, proof and wire forms of one concept have explicit,
   lossless relationships. Keep multiple forms only for a demonstrated ownership or workflow
   need. Avoid a second independently maintained semantic model.
5. **Experience:** a reader of the spec can find the corresponding SDK capability, and a reader
   of a public SDK concept can find its authority or implementation rationale.

Alignment does not mean one file per spec paragraph, exposing every internal stage, or giving
all languages identical object lifetimes. It means that those extra structures explain the
same model and do not become competing domain concepts.

## 4. Target conceptual organization

```mermaid
flowchart TD
  D[OBI document] --> O[Operations]
  D --> S[Sources: kind and optional data]
  D --> B[Bindings: operation, source and optional data]
  D --> P[Dependencies: operation and optional kinds]
  D --> M[Named schemas]
  B -->|names by key| O
  B -->|names by key| S
  P -->|names by key| O
  O -->|optional input and output| V[Schemas and reference environment]
  M --> V
  K[Kind implementation] -->|interprets| S
  K -->|interprets binding data with source data| B
```

The document declares relationships. It is not a runtime, a registry, an execution plan, or
proof that a realization works. A dependency does not select a provider. A schema reference
never turns arbitrary source data into one of the document's schemas.

| Responsibility | Intended home and boundary |
| --- | --- |
| Document vocabulary | Core document/model area: operation, source, binding, dependency, schema and example; authoring/read forms grouped around those concepts |
| Exact representation and editing | Supporting JSON/storage/edit machinery; preserves values, absence, untouched bytes and revision ownership without interpreting kind data |
| Conformance | One rule inventory and evidence model for OBI-01–14; structural checking and semantic rule checking remain distinguishable |
| Schemas and references | Core schema area for placement, identity, references and evaluation requests; optional evaluator implements value judgment |
| Default evaluation | Separate companion; compilation, projections, caches and limits are implementation mechanisms, not OBI objects |
| Schema comparison | Optional `openbindings-schema-comparison` companion for the adopted profile; implement the identity slice needed for pulling before claiming broader compatibility support |
| Binding/operation invocation | `openbindings-invocation`, with distinct binding and operation responsibilities and a shared bounded lifecycle where justified |
| Source pulling | `openbindings-source-pull`, exposing `SourcePuller` and the current additions/report vocabulary |
| Kind description/checking | `openbindings-kind-description`, exposing separate `KindDescriptor` queries and `SourceChecker::check_source` |
| Shared role values | A narrowly scoped shared home for context/challenges and genuinely shared carriers; never a miscellaneous domain framework |
| HTTP discovery | Separate companion; acquisition does not supply a base URI to document semantics |
| Wasm and TypeScript | Host representation and ownership adapters over the same semantic implementation |

These are responsibility and package decisions; exact internal module splits are established
by the model/API exercise in stage 1. Core has no dependency on invocation, pulling, kind
description, comparison, HTTP, a concrete kind, or an async runtime. Companions depend inward.
Concrete kind implementations depend on the SDK; applications compose providers and hosts.

Use small role-specific provider traits and checked callers. Implementing invocation must not
force implementation of checking, describing, or pulling. Do not introduce an all-purpose
`Kind` supertrait, registry, public projection language, or execution framework without an
actual consumer need and an alignment-map justification. Shared helpers can implement common
policy without turning every helper into an extension contract.

### Vocabulary and representation decisions

| Existing surface | Target direction |
| --- | --- |
| `Source`, source views/edits, `Binding.source` | Keep the concepts; their current type layout may be replaced |
| Source/binding `content` | `data` in authoring, reads, serialized field sets, diagnostics and TypeScript |
| `ValueContract`, `PreparedValueContract` | `Schema`, `PreparedSchema`; distinguish a contextual schema from arbitrary JSON and a compiled evaluator |
| Evaluator trait currently named `PreparedSchema` | `SchemaValidator`, so the provider's validator is not confused with the caller's prepared schema |
| `ValueContract::schema()` | `Schema::value()` for its exact schema value; retain original reference context independently |
| Supplied-schema `ResourceSet` family | `ExternalSchemas` / `ExternalSchema` / `ExternalSchemaError`; names reflect supplied external schemas, not a deleted document field |
| JSON Schema resource identities and locations | Retain "schema resource" where that is the actual concept; do not globally rename `resource` |
| `ContextChallenge` | Current `{message, schema}` shape; remove old requirement-family interpretation |
| `BindingValue` and source-plus-binding request | Replace with document-plus-key requests and views of that same revision; no detached legacy carrier as a second binding model |
| Inspector/synthesizer targets and coverage wrappers | Remove; introduce only the current source-puller report concepts and necessary implementation mechanisms |
| Per-role `SupportedKind` / `KindSupportVerdict` APIs | Replace public support-query surface with the kind-descriptor operations; internal provider routing remains an explicitly owned mechanism |

Validate the proposed signatures with small Rust and TypeScript callers before implementing
internals. Names are not a reason to preserve an unsuitable old object graph. No deprecated
aliases, dual `content`/`data` reading, old role adapters, or old wire envelopes are required.

## 5. Required semantic changes

### Document and schemas

- Source is `{kind, data?, description?}`; binding is `{operation, source, data?, ...}`.
  Sources remain, and kind remains on the source. Reject old unprefixed `content`, binding
  `kind`, and root `resources` through the current structural rule. Allow their literal names
  inside opaque data where appropriate. Absence and present `null` remain different.
- Retain OBI-04's actual named maps and aliases. OBI-07 checks the binding's source key;
  missing/empty/non-string source `kind` belongs to OBI-02, not a redefined OBI-07.
- Resolve operation aliases in their flat namespace. Binding/dependency operation references
  name operation keys. A dependency's kinds constrain the kind of the binding's source by
  exact equality; no normalization, version negotiation, ranking, or automatic provider choice.
- Implement current OBI-12 throughout conformance, reference inspection and evaluation: allow
  pointers into identified/nested resources with their proper bases; check references into
  contained resources from all contained schemas; use initial `$dynamicRef` resolution;
  distinguish invalid contained targets from external references and malformed URI references.
  Respect the final rule's exclusion when OBI-13 supplies no compared base.
- Implement OBI-14 for every schema in the document resource, including unused named schemas
  and a malformed `$dynamicAnchor` member. An identified resource is outside that prohibition.
  Schema-shaped data under source/binding data, examples, extensions, `const`, `enum` or unknown
  keywords is not admitted to schema inventory merely because it looks like a schema.
- Reconcile OBI-01–13, not only the visibly changed rules: escaped surrogate exclusions,
  version declaration, exact strings/numbers, meta-schema behavior, relative/absolute IDs,
  anchors, and rule applicability all follow the target text. Reports cover all 14 rules.
- Keep document conformance, a value's validity, an undefined result, unavailable information,
  evaluator capability failure, and author-claim truth distinct. Limits must not manufacture
  conformance violations or false satisfies/fails answers. Core never fetches references.
- There is no generic shared-value lookup/expansion, document `resources` API, automatic
  source/binding merge, or document-pruning algorithm to implement. A kind owns data references.
  A schema copied from an artifact needs the kind's dialect/reference translation, not in-place
  promotion into the OBI schema environment.

Generated output should follow §5's table order for readability: `openbindings`, `name`,
`version`, `description`, `operations`, `sources`, `bindings`, `dependencies`, `schemas`.
This is an SDK presentation convention, not semantic JSON member order or JCS canonicalization.
Parsed documents and untouched edit regions keep their authored order and bytes.

### Current optional interfaces

- **Binding invocation:** accept `{interface, binding, context?}` with a binding key. Deliver
  the document and key without losing context or exact data. The kind interprets source data,
  binding data and what they reference; binding invocation neither selects an operation binding
  nor validates operation values. It does not inspect the operation on the kind's behalf.
- **Operation invocation:** resolve operation names/aliases or an explicit binding, honor the
  ordered selection contract, reject unresolved multiplicity, validate each declared input and
  output before forwarding, and invoke the selected document/key. No silent preference ranking.
  Relay unsuccessful completion and context challenges without output-schema validation.
- **Context:** use an opaque supplied object and `{message, schema}` challenges, with the
  documented `oauth2` annotation. Preserve challenges through operation invocation and preflight.
  `CONTEXT_REQUIRED` is permitted only before output and observable operation effects. The SDK
  does not acquire credentials, open URLs, store secrets, or retry automatically.
- **Kind description:** implement `listKinds`, `describeKind`, `checkSource`; support is per
  operation key, not a universal kind boolean. Preserve source-data/binding-data schemas and
  `check.description` / `check.executes`. A check keeps the input kind and returns the source
  entry the kind stands behind. Invocation alone does not require a descriptor. Disclosing an
  executing check is distinct from application consent and from performing that check.
- **Source pulling:** take `{interface, source, context?}` and return `{additions, report}`.
  Add only new operations/schemas/bindings, with bindings naming that source. Report existing
  entries as current/stale/unmatched, proposals and their change classes, omissions, reuse,
  dependencies through `uses`, loss and exhaustiveness. Never apply a proposal, overwrite an
  existing entry, remove an unmatched binding, or perform a source operation during a pull.
- **Pull ownership:** the kind projects source offerings without reading the destination's
  operations to choose names/shapes; kind-neutral assembly owns collision/reuse rules. Kind
  code supplies interpretation of existing data, dependency information for opaque data, and
  fidelity/change judgments. SDK code cannot infer `uses` by scanning unknown data for `$ref`.
  The API exercise must show how those responsibilities compose without inventing a universal
  target-address format. Check verifiable report relationships without claiming to certify
  fidelity, exhaustiveness or the truth of a kind's change classification.
- **Reuse comparison:** use the profile's normalized identity, including exact values and
  the specified handling of unions and annotations; not byte equality, generic JSON equality,
  hash equality alone, or general schema equivalence. Identity has equal/different results,
  not the subsumption profile's `indeterminate`. Normalization/reference/resource failures
  remain explicit failures and cannot justify a false reuse or a false claim of difference.
  Default SDK policy is to fail a pull whose necessary comparison cannot complete, with an
  implementation diagnostic; any later partial-result policy must fit the interface explicitly.
- **Complete pull:** `exhaustive` and no `implementation-unsupported` omission, exactly as the
  interface defines it. Invalid/excluded/conflict omissions and disclosed loss do not by
  themselves negate that condition. Stricter caller requirements are separate policies.

Default checked SDK entry points may require a conformant document and refuse malformed
provider results. Document that as SDK admission policy: the interfaces' open document carriers
are not conformance certificates and do not prescribe validation timing or error precedence.

## 7. Validation gates

### G1. Provenance and traceability

- All published claims name exact applied spec/interface/companion/profile revisions, separately
  from package versions. Embedded schemas and frozen inputs match their declared sources.
- The obligation map covers every specification rule and each adopted interface capability.
  Each implementation mechanism and policy has a reviewed justification and an owner.
- Reconcile all old 440 core cases and 1,566 evaluator-kit IDs: retained, rewritten for the new
  rule, moved to the appropriate layer, or retired with an explicit reason and replacement
  coverage where needed. Old expected answers are not invariants. Do not delete a failing case
