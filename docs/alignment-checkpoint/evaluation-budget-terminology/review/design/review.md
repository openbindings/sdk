# Evaluation budget terminology — bounded design GO with two clarifications

Reviewed `design/2026-11-02/evaluation-budget-terminology.md` against the actual `Limits`, Plan/Graph, selected-meta, Wasm and TypeScript paths. This is source/design review only: no SDK edits, builds or execution. The root-memo/State-copy candidate must remain a separate checkpoint. This approves a terminology-only implementation with the clarifications below, not a changed budget policy or final qualification.

## Ownership and naming

The pair `evaluation_sdk_work_units` / `evaluation_sdk_reservation_bytes` accurately describes the current built-in evaluator. Work is charged at explicit SDK sites, including size-dependent scans and proof traversal; it is not an instruction, callback or schema-node counter. Storage is a cumulative reservation estimate at SDK-owned sites, not retained program size, requested allocator bytes, live heap or a universal memory bound. The names distinguish these allowances from preparation's `max_sdk_*` counters and immutable pattern representation limits. Do not rename comparison/source-pull scoped allowances or diagnostic codes as collateral cleanup.

The proposed types/defaults match current source: optional work with `None` and reservation `48 * 1024 * 1024` (50,331,648). `None` removes the caller-selected work cap; fixed capability/structural bounds and cancellation remain. Each value invocation starts a fresh Graph allowance. When Explain follows an established failure, its second pass receives only the first pass's remaining work/storage; failure of that optional pass cannot replace the established failure. Failed diagnostic work is not refunded. Independent evaluations do not consume a persistent Plan-wide evaluation allowance.

**Clarification 1:** say selected-meta evaluation *debits* both its per-invocation evaluation allowances and the enclosing preparation Attempt, not merely that it “observes” the Attempt. `meta::validate` calls `evaluate_tracking_unavailable` with `Some(attempt)`; each consumer evaluation receives its ordinary Plan allowance while all those evaluations also share the preparation attempt's cumulative work/reservations. A renamed evaluation field can therefore cause a **preparation Limit** while evaluating a required custom meta-schema. This does not merge the two owners, make evaluation limits a single aggregate across all meta consumers, or apply an ordinary value-call Attempt where none exists. Existing preparation failure classification/codes must remain.

Replace “diagnostic work” in the reservation description with “diagnostic storage” (or describe work and storage together) to keep the dimensions clear. The intended boundary is otherwise correct. Update TypeScript's `totalPatternMemory` comment too: its reference to the “separate program allowance” should name the per-call evaluation reservation allowance. The stale guide sentence about single-build pattern construction is a documentation correction only.

## Public and private boundaries

Public Rust/serde uses only the new snake-case field names, with `deny_unknown_fields`. TypeScript uses only the new camel-case names, with existing known-key and numeric checks. No aliases or compatibility shim are needed for this greenfield API. The current generic encoder/decoder can carry these names without a new abstraction. Qualify against the rebuilt Wasm facade, because TypeScript's accepted key set is derived from that facade's returned default object; source-only type success cannot establish runtime key retirement with a stale artifact.

Preserve the existing domains: Rust uses target `usize`; TypeScript/Wasm admits nonnegative u32 values, allows null only for optional work/schema-resource fields, and rejects null reservation, fractions, negatives and out-of-range inputs. Do not accidentally clamp native Rust/benchmark values to the JavaScript domain or turn zero into a default. Keep ordinary unknown-option rejection, including mixed old/new objects whose values happen to agree or are null.

**Clarification 2:** the private frozen benchmark adapter must reject either replacement SDK spelling **even when present alone**, not only collisions with an old carrier key. Otherwise forwarding the map into the new serde type silently expands the frozen protocol. Reject new-only and mixed input using key presence, including null/zero. Translate the two historical carrier keys by moving their original JSON values to the new keys before ordinary deserialization. Do not coerce, reparse, default or normalize those values. Omitted keys retain defaults; work null remains None; invalid old-key values remain invalid. The separate historical `evaluation_depth` handling and all other carrier fields remain unchanged.

This adapter translation is outside the timed SDK operation; it must not move parsing, preparation, readiness/outcome assertions or allocation boundaries. Preserve fixtures, limits, expected observations, modes, archived baseline sources and receipts. The candidate instrument identity changes even though its logical requests do not. Existing identical-instrument helpers should still refuse the pair; a separately reviewed final matched pair binds the new candidate adapter and its actual source/lock/build provenance. No generic compatibility verifier should be relaxed merely to accept the rename.

## Bounded qualification additions

The draft's five validation gates are appropriate. Add explicit coverage for the two clarifications and map the following to existing tests where possible:

1. Default Rust serialization and rebuilt Wasm defaults expose exactly the replacement keys with unchanged values; neither old spelling leaks through a nested carrier. Round-trip omission/null/zero/positive limits without coercion.
2. Raw serde, direct Wasm JSON and TypeScript runtime/type controls reject old-only and old+new keys; nullable work remains distinct from zero, and reservation never accepts null. Preserve the current u32/usize domain distinction.
3. Low work/storage requests preserve the same outcome and diagnostic codes on ordinary value evaluation, and the same PreparationFailure classification for required meta evaluation. The separate preparation `max_sdk_*` controls remain unchanged.
4. Existing exact/one-below cumulative Explain and cancellation/earlier-cause checks use the same values after key renaming. Repeated calls still receive fresh allowances. A naming edit must not alter Graph call sites, optional-pass ordering or quota arithmetic.
5. Frozen benchmark carrier tests cover omitted limits, work null/zero/nonzero, reservation zero/nonzero, both historical keys together, malformed values, new-only keys and mixed-key collisions. Compare the same complete observations through the same logical job; do not substitute a preparation refusal for readiness.
6. Review the adapter as an allowed key-translation diff only. Preserve its readiness assertion, historical depth handling, timed/allocation regions and root/resource selection. Bind actual changed instrument/source digests; retain frozen request hashes.
7. Maintain an occurrence inventory distinguishing public/current source, frozen benchmark carrier, deliberate rejection tests and historical evidence. Broad textual replacement must not rewrite baseline archives, receipts, pinned inputs or performance tables. Rebuild declarations/reference material and refresh the current binding map and package/consumer artifacts before final qualification.

`controls.json` records these groups in a reusable bounded checklist. No new semantic oracle, default, resource waiver, benchmark acceptance or unrelated exhaustive audit is introduced.
